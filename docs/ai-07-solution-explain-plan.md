# AI-07 피해 대응 근거 설명 구현·테스트 계획서

작성일: 2026-11-16 · 상태: 1차 Spring 클라이언트 구현 완료, 2·3차 미연결

명세 출처는 AI-07 내부 API 초안 및 팀 공유 `WSID-API-Spec.md`의 AI-07·SOL-01~04 절(2026-11-16 제공본)이다. 이 문서는 단계별 개발·테스트 기준을 정리한다. 1차의 실제 변경 파일·검증 결과와 후속 연동 작업은 [구현 보고서](ai-07-solution-explain.md)를 참고한다. 아래 배열 요소·길이·보호 규칙은 Spring 초기 계약이며 FastAPI와 대조해 확정해야 한다.

## 1. 목표와 단계별 범위

`POST /internal/ai/solutions/explain`은 확인된 사실과 Spring이 승인한 근거 문단을 받아 대응 단계의 이유를 설명한다. AI-06은 사실을 추출하고, Spring 규칙은 대응 카드를 선택하고, AI-07은 그 사실·근거를 설명한다. 설명 생성 때문에 사실·긴급 여부·카드·기관·연락처가 바뀌어서는 안 된다.

| 단계 | 개발 범위 | 완료 기준 |
|---|---|---|
| 1차 Spring 클라이언트 | 요청·응답 DTO, fake/HTTP, 타입·참조 코드 대조, 출력 제한, 계약·전송 테스트 | 입력 계약에 맞춰 호출하고 구조·제약을 통과한 결과 또는 사용 불가 예외 반환 |
| 2차 FastAPI | 승인 문단 내 검색/선별·설명 생성, 근거 충실성·출력 보호, 내부 인증·추적 | 승인 범위를 벗어나지 않는 설명과 실제 사용한 근거 코드 반환 |
| 3차 상담·콘텐츠 연결 | 승인 근거 카탈로그·사실/카드 규칙·소유권·저장·공개 응답 | 긴급 안내를 우선 제공하며 검증된 보조 설명을 제공·복원 |

1차에는 FastAPI·벡터 DB·콘텐츠 로더·SOL 서비스·컨트롤러·DB 마이그레이션을 구현하지 않는다. 클라이언트가 생겨도 실제 상담에서 호출되는 것은 아니다.

## 3. 요청 계약 제안

```http
POST /internal/ai/solutions/explain
Content-Type: application/json
X-Internal-Api-Key: <환경 설정값>
X-Request-Id: <요청 UUID>
```

배열 요소를 구체화한 아래 예시는 합성 데이터다. 실제 기관 안내나 승인 완료 콘텐츠가 아니다.

```json
{
  "facts": {
    "transferredMoney": "YES",
    "contactContinues": "UNKNOWN"
  },
  "verifiedReferences": [
    {
      "code": "REF_EXAMPLE_V1_P1",
      "title": "대응 단계 확인 예시",
      "excerpt": "확인된 사실에 해당하는 검토된 대응 카드의 순서와 준비 항목을 확인합니다."
    }
  ]
}
```

| 값 | 1차 검사 제안 |
|---|---|
| facts | null·빈 Map 거부. 부분 Map 허용. AI-06과 같은 4개 키만 허용 |
| 사실 값 | 정확히 YES·NO·UNKNOWN 문자열. UNKNOWN을 NO로 취급하거나 추정하지 않음 |
| verifiedReferences | 필수 List, 빈 배열 허용, 최대 10개. null 요소 거부 |
| 각 근거 code | 필수 문자열, `[A-Z0-9_]{1,100}`, 요청 안에서 중복 거부 |
| title | 공백 불가, 최대 200자 |
| excerpt | 공백 불가, 최대 2,000자. 원문 전체 대신 승인된 필요한 문단만 전달 |
| requestId | Java DTO에 UUID 필수. JSON 본문 제외, X-Request-Id 헤더로 전달 |

문자 수는 초기 Spring 구현에서 Java String.length 기준으로 검사한다. Python의 길이 계산과 이모지 경계 사례를 맞춘다. 문자열을 임의 절단하거나 잘못된 항목을 조용히 제외하지 않는다. Map·List는 방어적으로 복사한다.

`facts`의 키·값 계약은 AI-06 요청 DTO의 같은 ai 패키지 상수를 재사용하는 방안이다. `solution` 도메인에 의존하지 않는다. 후속 확장 시 두 API가 같은 사실 정의를 사용하는지 테스트한다. DTO의 toString은 사실 값·제목·근거 문단 대신 길이·개수·요청 ID만 표시한다.

### 승인 여부를 확인하는 위치

`VerifiedReference`라는 DTO 이름이나 올바른 code 형식이 실제 승인을 증명하지는 않는다. 1차는 필드 형식만 검사한다. 3차 호출 서비스는 검토 완료·출처·확인일·현재 유효한 버전을 확인한 카탈로그에서만 DTO를 구성한다. 공개 요청에서 사용자가 보낸 근거·코드·URL을 그대로 승인 근거로 취급하지 않는다.

code는 승인된 특정 버전의 문단을 식별하도록 관리한다. 예시의 V1/P1 표기는 제안일 뿐이며 실제 코드 체계는 콘텐츠 담당자와 정한다. 같은 코드에 다른 문단을 덮어쓰지 않고 재현 가능한 버전을 유지하는 방안을 우선한다. 출처 URL·확인일·승인 상태 등 관리 정보는 Spring 카탈로그에 보관하며, 위 최소 요청에 관리 필드를 모두 전송하지 않는다.

### 근거가 없거나 사실이 미확정인 경우

초안과의 호환을 위해 DTO·HTTP 계약은 `verifiedReferences: []`를 허용한다. 이때 응답 referenceCodes도 반드시 빈 배열이어야 한다. 그러나 정상 JSON을 받았다는 이유로 근거 없는 자유 생성 설명을 사용자에게 노출하지 않는다.

3차 서비스는 승인 근거가 없으면 AI-07 호출을 생략하고 기존 검토된 카드 또는 고정 안내만 제공한다. 사실이 모두 UNKNOWN이면 추가 질문·직접 선택 흐름을 우선한다. 설명 생략을 상담 실패나 사실 초기화로 처리하지 않는다. AI 호출을 생략하는 규칙은 DTO가 아닌 호출 서비스의 책임이다.

## 4. 성공 응답과 참조 코드 검증

```json
{
  "success": true,
  "data": {
    "explanation": "검토된 대응 카드의 순서와 준비 항목을 함께 확인해 주세요.",
    "referenceCodes": ["REF_EXAMPLE_V1_P1"]
  }
}
```

| 필드 | 1차 검사 제안 |
|---|---|
| success | 실제 JSON boolean true. 문자열 "true"·숫자 1 거부 |
| data | 객체 필수 |
| explanation | 실제 문자열, 공백 불가, 최대 2,000자. 일반 텍스트로 반환 |
| referenceCodes | 필수 문자열 배열, 최대 10개. 코드 형식·중복 검사. 빈 배열도 필드를 생략하지 않음 |
| 요청과의 대조 | 반환 코드 전부 요청의 verifiedReferences에 존재해야 함. 요청 근거 전체를 인용할 필요는 없음 |
| 근거가 1개 이상 있는 요청 | referenceCodes도 최소 1개 있어야 함 |
| 근거가 비어 있는 요청 | referenceCodes도 반드시 빈 배열이어야 함 |

`JsonNode`로 루트·success·data·문자열·배열·요소 타입을 확인한 뒤 `treeToValue`로 변환한다. Jackson 3의 isString을 사용한다. null 배열을 빈 배열로 바꾸거나 알 수 없는 코드를 조용히 버리지 않는다. 추가 data 필드는 무시하되 공개 응답으로 전달하지 않는다.

요청과 응답을 함께 받는 `SolutionExplanationValidator`를 신규 제안한다. DTO에서는 각 값의 형식을 검사하고, 이 검증기에서는 반환 코드가 요청 집합의 부분집합인지·근거가 1개 이상이면 인용도 최소 1개인지·근거가 비어 있으면 반환 코드도 비어 있는지·출력 제한을 통과하는지 검사한다. fake와 HTTP가 같은 검증기를 사용해 계약이 달라지지 않도록 한다.

**참조 코드가 올바르다고 설명 내용까지 근거에 부합하는 것은 아니다.** 1차에서 보장하는 것은 구조·코드 연결·명시된 출력 제약이다. 사실을 뒤집거나 출처에 없는 대응을 덧붙이는 문제는 FastAPI의 근거 충실성 검증·모델 평가와 후속 표시 전 검증에서 별도로 다룬다.

## 5. 연락처·링크와 출력 보호 정책

초안의 “출처에 없는 전화번호/링크 생성 금지”를 위해 초기에는 **설명 본문에 연락처·URL을 넣지 않는 방안**을 제안한다. 승인된 연락처라도 실제 버튼·전화·링크는 Spring이 검토된 카드에서 조회해 별도 필드로 제공한다.

기관 표현은 `은행`·`경찰`·`공식 신고 채널` 같은 일반 범주를 허용하고, 특정 은행·관서 등 구체적인 기관명은 생성 설명에 넣지 않는 방안을 제안한다. 구체적 기관과 실제 연락처는 검토된 카드에서만 제공한다. 일반 범주라도 사실·근거에 없는 새 행동을 권하는 것은 허용하지 않는다. 이 허용 범위와 일반/구체 명칭 판별 기준은 FastAPI와 합의해야 한다. Spring 1차의 URL·전화번호 패턴 검사는 기관명의 의미를 판별하지 않으므로 구체적 기관명 금지까지 보장한다고 표시하지 않는다.

명세의 `verifiedReferences: []`, `referenceCodes: []` 예시에 나온 “은행과 공식 신고 채널”은 일반 범주 표현으로 볼 수 있다. 다만 그 문장에 대응하는 승인 근거는 예시에 없으므로 근거 충실성이 확인된 응답으로 취급하지 않는다. 해당 예시가 1차 타입·코드 검사를 통과하더라도 3차 서비스는 빈 근거 요청의 호출을 생략하며, 이를 그대로 노출하는 기준으로 사용하지 않는다.

3차에서 Spring이 요청 문단을 구성할 때는 **연락처·URL을 제외한 설명용 문단을 별도로 승인해 excerpt로 전달**한다. 원본 출처·전화·링크는 카탈로그/카드에 유지한다. 연락처가 있는 원문을 그대로 보내고 프롬프트에만 의존하지 않으며, 정규식으로 일부를 잘라 의미가 달라진 문장을 자동 승인하지 않는다. 설명용 문단을 준비하지 못하면 AI-07을 생략한다.

1차 검증기는 명시적 URL 스킴·www·일반적인 전화번호·HTML/Markdown 링크 등 합의된 금지 패턴이 설명에 있으면 전체 결과를 사용 불가로 처리한다. 문자열을 부분 삭제해 문장의 의미를 바꾸지 않는다. 허용하는 문장부호와 숫자까지 무조건 거부하지 않도록 정상/오탐 경계 테스트도 둔다.

정규식만으로 우회 표기·모든 언어의 연락처·근거 밖의 의미를 완전히 판별할 수는 없다. 따라서 이 검사 통과를 “출처 검증 완료”로 표시하지 않는다. FastAPI는 연락처·링크 생성 금지와 근거 충실성을 출력 단계에서 확인하고, 운영 연결 전에 우회 표현·새 기관·근거 없는 행동 추가를 별도로 평가한다. 충족하지 못하면 자유 생성 설명 노출을 보류하고 검토된 고정 안내로 전환한다.

프론트는 설명을 일반 텍스트로 표시한다. HTML 실행·Markdown 링크 활성화·자동 링크 변환은 하지 않는다. 출처 링크는 AI 설명에서 추출하지 않고 Spring의 승인 코드 조회 결과로만 구성한다. 이 화면 계약과 표시 전 검증은 3차 범위다.

## 6. 실패·설정·추적

| 상황 | 처리 계획 |
|---|---|
| 요청 null·형식/길이/중복 위반 | IllegalArgumentException. 입력 구성 오류를 AI 장애로 숨기지 않음 |
| HTTP 오류·타임아웃·깨진 JSON·success false·응답 계약/코드/출력 제한 위반 | AiUnavailableException. cause나 본문을 붙이지 않음 |
| 설명 생성 불가 | 3차에서 기존 카드·확정 사실을 유지하고 설명만 생략/고정 안내로 대체 |
| 긴급 카드가 적용됨 | 기존 상담 정책에 따라 AI-07 생략. 검색·생성 완료를 기다리지 않음 |

기존 공통 restClient와 connectTimeout/readTimeout을 사용한다. 현재 기본값은 연결 2초·응답 20초이고, AI-03·05 전용 응답 제한과 분리된다. 1차에서는 AiProperties·application.yml·HttpAiClient 생성자를 변경하지 않는다. RAG 지연이 공통 제한에 맞지 않으면 측정 후 전용 클라이언트·설정·분리 테스트를 함께 추가한다.

자동 재시도는 하지 않는다. 요청 ID는 본문에서 제외하고 헤더로 추적한다. 같은 논리 요청의 재시도는 같은 ID로 연결하고, 시도 구분이 필요하면 별도 번호를 기록한다. 헤더만으로 FastAPI의 중복 처리나 DB 중복 저장 방지가 구현되지는 않는다.

사용자 피해 설명 원문·계좌·전화·인증정보는 AI-07 요청에 넣지 않는다. 구조화된 사실과 필요한 승인 문단만 보낸다. HTTP/LLM/프록시/APM의 본문·오류·디버그 로그에서도 원문과 문단을 수집하지 않도록 설정한다. 추적은 요청 ID·처리 시간·개수·고정 실패 분류로 제한한다.

fake는 근거가 있으면 고정 보조 설명과 요청의 첫 근거 코드 하나를 반환하는 방안이다. 근거가 없으면 “확인된 근거가 없어 추가 설명을 제공하지 않습니다.”와 빈 코드를 반환한다. `[AI_FAIL]` 같은 실패 재현이 필요하면 합성 근거 제목의 명시적 표식으로만 처리하고 그 문구를 예외·결과에 복사하지 않는다.

따라서 표식에 의한 fake 실패 재현은 **근거가 1개 이상 있는 요청에서만 가능**하다. 빈 근거 요청에는 실패 표식을 넣을 수 없다. 빈 근거에서 통신 실패를 검증할 필요가 있으면 HTTP 목업이나 예외를 반환하는 AiClient 테스트 스텁을 사용한다. 3차 서비스의 빈 근거 경로에서는 AI 미호출을 검증한다. fake는 실제 검색·의미 분석 품질을 검증하는 수단이 아니다.

## 9. 후속 상담·콘텐츠·DB 연결

1. **승인 근거를 확보한다.** content에 문서/문단 코드·버전·출처·확인일·검토 상태를 관리할 모델·로더를 추가한다. 카드 ID와 근거 문단 코드를 같은 것으로 가정하지 않는다. 규칙과 현재 사실에 해당하며 연락처·URL이 없는 승인된 설명용 문단만 골라 요청을 구성한다. 연락처와 출처 링크는 카드·카탈로그에서 별도로 제공한다.
2. **긴급 흐름을 먼저 결정한다.** Spring의 ResponseRules가 긴급 여부·대응 카드를 정한다. 긴급이면 AI-07을 호출하지 않고 검토된 카드부터 제공한다. 비긴급에서도 근거가 없거나 사실이 전부 미확정이면 설명을 생성하지 않는다.
3. **트랜잭션 밖에서 호출한다.** 상담 소유권·현재 사실·상태·버전·승인 문단 버전을 읽고 호출한다. 저장 시 상태·버전·소유권·근거 유효성을 다시 확인한다. 호출 중 사실 수정·상담 종료·근거 철회가 있으면 오래된 설명을 반영하지 않는다.
4. **표시 전 검증한다.** 코드 등록/버전/승인 여부와 적용 사실·카드의 일치, 설명의 근거 충실성·출력 제한을 확인한다. 자동 의미 검증의 범위·실패 기준은 운영 전에 정하고, 미충족이면 설명을 생략한다. AI 설명으로 카드 순서·행동·연락처를 교체하지 않는다.
5. **저장 형식을 정한다.** SolutionMessage.referenceCodesJson은 저장 공간만 있고 갱신 경로가 없다. 코드 설정/조회 메서드·형식 검증을 추가하고 카드 코드와 문단 코드를 구분한다. 재현을 위한 근거 버전/식별 정보도 설계한다. 사용자 원문·추출 근거는 저장하지 않고, 생성 설명은 검증·개인정보 확인 후 safeContent 저장/보관 여부를 정한다.
6. **공개 API를 정한다.** 현재 SOL 응답에 explanation·근거 출처·생성 상태를 어떻게 제공할지 확정하지 않았다. 명세에 없는 필드를 몰래 추가하지 않고 카드·설명 생략·복원 정책을 프론트와 맞춘다. 비회원 소유권·만료/복원은 기존 상담 선행 과제다.

기존 [SolutionMessageRepository](../src/main/java/com/wsid/solution/repository/SolutionMessageRepository.java)의 요청 ID 조회와 [V2 제약](../src/main/resources/db/migration/V2__add_constraints.sql)의 상담별 요청 ID/순서 유일성을 활용하되 동시 생성 충돌을 서비스에서 처리한다. 현재 회원 user_id NOT NULL 구조에 비회원이 자동 지원되는 것은 아니다. 1차는 이 저장·소유권 구조를 변경하지 않는다.

## 11. 구현 전 합의·완료 기준

- verifiedReferences의 code/title/excerpt 구조, 필드명·문자 길이·개수, 근거 코드/버전 체계를 확정한다.
- Spring 승인 카탈로그와 FastAPI 검색 인덱스의 책임·동기화·철회 정책, 요청 밖 근거 사용 금지를 합의한다.
- 설명 본문의 연락처/URL 금지·텍스트 표시 정책, 금지 패턴과 의미 검증의 한계·실패 시 설명 생략 기준을 합의한다.
- 일반 기관 범주 허용·구체적 기관명 미사용이라는 초기 제안을 검토하고, 명칭의 구분 기준·FastAPI 검증 책임을 확정한다. 명세의 빈 근거 예시를 출처 검증 완료 사례로 취급하지 않는다.
- Spring이 연락처/URL 없는 설명용 문단을 별도 승인해 보내고 실제 연락처는 카드에 남기는 방안을 확정한다. 프롬프트만으로 연락처 복사를 막는 방식은 초기안으로 채택하지 않는다.
- 빈 근거 요청의 계약상 허용과 실제 서비스 호출 생략을 구분한다. 요청 근거가 1개 이상이면 반환 코드도 최소 1개, 요청 근거가 없으면 반환 코드도 빈 배열이라는 규칙을 합의한다.
- fake 실패 표식은 근거가 있는 요청에서만 사용할 수 있다. 빈 근거의 실패 시나리오는 HTTP 목업/테스트 스텁으로, 서비스 생략 경로는 미호출 검증으로 나누어 테스트한다.
- 실패 HTTP 상태·필수 빈 배열 직렬화·요청 ID·재시도·본문 로그/공급자 보관 설정을 맞춘다.
- 공통 20초 제한의 적합성을 측정하고 필요할 때 전용 설정을 추가한다. 상담의 전체 응답 시간·취소 정책과 구분한다.
- 공개 설명/출처 필드·저장/보관·근거 버전 재현·비회원 소유권 및 긴급 경로 미호출 정책을 확정한다.

1차 완료는 클라이언트·엄격한 타입/코드 대조·합의한 출력 제한·테스트·구현 보고서까지다. 전체 기능 완료는 승인 콘텐츠 확보, 실제 모델의 근거 충실성 평가, 상담 서비스·DB·공개 API 연결 검증까지 포함한다.
