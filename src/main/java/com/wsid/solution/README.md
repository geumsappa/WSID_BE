# solution — 실제 피해 대응

사용자가 '사기가 의심돼요 / 피해를 당했어요'를 누른 뒤의 흐름을 맡아요.
틀리면 실제 피해로 이어지는 부분이라, **카드 선택과 긴급 여부는 코드 규칙으로만 정해요.**

## 명세서 매핑

| 명세서 항목 | ID | 우선순위 | 상태 | 관련 코드 |
|---|---|---|---|---|
| 피해 설명 또는 선택으로 시작 | SOL-003 | 상 | 엔티티만 | `SolutionSession.start` |
| 설명에서 확인 항목 추출 | SOL-003 · I5 | 상 | 미구현 | `facts_json` 컬럼 |
| 필요한 항목 추가 질문 | SOL-003 | 상 | 미구현 | `next_question_json` 컬럼 |
| 파악된 내용 수정 | SOL-003 | 상 | 미구현 | - |
| 분석 실패 시 직접 선택 | SOL-003 | 상 | 미구현 | `InputKind.OPTION`, `selected_code` |
| 긴급 안내 우선 표시 | SOL-007 | 상 | 미구현 | - |
| 필요한 대응 카드 제공 | SOL-004 | 상 | 미구현 | `card_codes_json` 컬럼 |
| 확인한 사실과 카드 다시 보기 | SOL-004 | 중 | 미구현 | - |
| 공식 근거 문단 검색 | SOL-004 · I6 | 중 | 미구현 | `reference_codes_json` 컬럼 |
| 피해 설명의 민감정보 처리 | 비기능 · I5 | 상 | 미구현 | `safe_content` 컬럼 |

## 테이블

- `solution_sessions`: 확인한 사실, 적용된 카드, 다음 질문 → `domain/SolutionSession`
- `solution_messages`: 대화 한 줄. `safe_content`에는 민감정보를 가린 내용만 저장 → `domain/SolutionMessage`

## 개발 순서

training 패키지와 같은 모양으로 만들어요.

1. **domain 규칙부터**: 사실을 값 객체로 만들어요. 항목은 송금, 정보 제공, 앱 설치, 연락 지속이고 값은 예·아니오·모름이에요.
   `SolutionSession`에 `mergeFacts(...)`(바꾼 항목만 갱신)를 추가하고, `ResponseRules`(사실 → 카드 코드 목록, 긴급 여부, 다음 질문)를 순수 Java로 만들어요.
2. **단위 테스트**: "보냈다", "보내려다 멈췄다", "송금을 언급하지 않았다"가 구분되는지, 긴급 카드가 맨 앞에 오는지, 모름일 때 더 안전한 쪽 안내가 나오는지 검증해요.
3. **AI 연결**: `AiClient`에 사실 추출(I5) 메서드를 추가해요. 실패하면 화면에서 직접 선택하게 해요. 선택으로 확인한 사실도 같은 규칙에 넣어요.
4. **service**: 읽기 → AI 호출(트랜잭션 밖) → 사실 합치기 → 규칙 적용 → 저장. `content`에서 카드 내용을 가져와 응답을 만들어요.
5. **controller**: 시작, 메시지 전송, 사실 수정, 다시 보기.
6. **근거 검색(I6)**: 긴급 카드가 없을 때만 호출해요. 긴급 카드는 검색을 기다리지 않아요.

## 규칙

- 기관명, 연락처, 링크는 `content`의 검토된 카드에서만 가져와요. AI가 만든 값은 쓰지 않아요.
- 피해 설명 원문과 추출 근거는 DB와 로그에 남기지 않아요.
- 확인하지 못한 항목은 '모름'으로 유지해요. 추측해서 '아니오'로 바꾸지 않아요.
- 지난 질문의 선택지는 다시 적용하지 않아요. `next_question_json`과 요청의 질문 ID가 다르면 최신 상태를 다시 불러오게 해요.

## 정할 것

- 로그인 없이 피해 대응을 쓸 수 있게 할지 (지금 ERD는 로그인 필수)
- 훈련 중 실제 피해를 밝혔을 때 어느 훈련에서 넘어왔는지 연결할 컬럼
- 근거 문단의 화면 표시 여부와 공개 API 필드
